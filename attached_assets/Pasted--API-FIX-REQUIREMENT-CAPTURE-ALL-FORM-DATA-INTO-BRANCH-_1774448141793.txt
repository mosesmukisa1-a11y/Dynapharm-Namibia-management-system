# API FIX REQUIREMENT — CAPTURE ALL FORM DATA INTO BRANCH SALES + RELEVANT PORTALS

## Main problem to fix

Clients are physically attending the branch today, but the daily report still shows **0** for sections that should contain activity.

This means:

* the form is being filled
* the client exists in branch activity
* but the transaction is **not being mapped into the reporting engine**
* or the record is saved without a **sale category / branch / workflow status**
* or consultation/prescription records are saved separately and never posted into branch sales summary tables

The system must stop treating these records as isolated forms.

Every submitted branch-facing form must create a **real transactional record** that updates:

* Branch Sales
* Branch Dashboard
* GM Portal
* MIS Portal
* Director Portal
* Finance Portal where relevant
* Stock deduction flow where relevant
* Consultation / Prescription logs where relevant

The report must only show **0** when there was truly no client activity at that branch on that date.

The current report confirms that totals are being generated, but category-level capture is incomplete.

# 3) Classification rules

The backend must not wait for the report page to guess categories.

It must classify on save.

## Rule mapping

* `activity_type = consultation` or `full_body_checkup`

  * update **Consultation Fees**
  * update branch daily client count
  * update consultant dashboard
  * update GM / MIS / Director consultation analytics

* `activity_type = walkin_sale`

  * update **Walk-in Sales (General)**
  * deduct stock
  * update branch sales totals
  * update finance

* `activity_type = member_sale`

  * update **Member Sales**
  * attach NB number
  * deduct stock
  * update distributor-linked sales analytics

* `activity_type = non_member_sale`

  * update **Non-member Sales**
  * if referral exists, store referral NB
  * deduct stock
  * update branch revenue

* `activity_type = online_order`

  * update **Online Order Sales**
  * only after payment/branch receipt confirmation
  * deduct stock when fulfilled by branch

* `activity_type = prescription_dispensing`

  * update **Prescription Dispensing**
  * deduct stock
  * link to prescription id
  * update consultant/branch logs

# 4) Reporting engine endpoint

## `GET /api/reports/branch-sales/daily?branch_id=WINDHOEK_CBD&date=2026-03-25`

This endpoint must not read from random UI state.

It must aggregate directly from `branch_activity_transactions`.

### Aggregation logic

```ts
consultationFees = SUM(grand_total where activity_type in ['consultation','full_body_checkup'] and payment_status='paid')

walkInSales = SUM(product_total_dp where activity_type='walkin_sale')

memberSales = SUM(product_total_dp where activity_type='member_sale')

nonMemberSales = SUM(product_total_dp where activity_type='non_member_sale')

onlineOrderSales = SUM(product_total_dp where activity_type='online_order' and payment_status='paid')

prescriptionDispensing = SUM(product_total_dp where activity_type='prescription_dispensing')

totalTransactions = COUNT(*)
totalQtySold = SUM(total_qty)
grandTotal = consultationFees + walkInSales + memberSales + nonMemberSales + onlineOrderSales + prescriptionDispensing
```

### Important

If there are consultation forms completed today in that branch, then **Consultation Fees must not show 0**.

If there are prescriptions dispensed today, then **Prescription Dispensing must not show 0**.

If clients were attended but not yet paid, the report should show:

* activity count
* unpaid count
* pending payment value

instead of hiding them as zero.

Then show on dashboard:

* clients checked in
* clients seen

* clients pending payment
* clients with prescriptions

This prevents false impression that nobody came.

# 9) Stop zero values caused by bad joins

Common cause of current bug:

* consultation form saves in `consultations`
* sales save in `sales`
* report page only reads `sales`
* therefore consultation section stays zero

Fix:
Every finalized workflow must write a normalized record into:

## `branch_activity_transactions`

No exception.

# 11) Validation rules

The API must reject incomplete records.

* branch_id
* service_date
* activity_type
* workflow_source
* client_name or client_id
* captured_by

### Conditional:

* `nb_number` required for `member_sale`
* `referral_nb` optional for non-member, default to `NB00 5676` if business rule says so
* product items required for all stock-impact sales

# 12) Report display rule

The report must not simply display 0 because category amount is empty.

Instead:

### show:

* `0` only if there were truly no records
* `Pending capture` if raw visit/form exists but posting failed
* `Unpaid` if service happened but payment not completed
* `Draft` if started but not finalized

This will make branch reports honest.
